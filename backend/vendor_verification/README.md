# Authentic clipboard verification framework

Current status: **0 authentic captures, 0 reviewed vendor expected-output artifacts, 0 approved releases.** `manifest.json` is deliberately empty. The pending example contains no captured content, hash, review, mapping or compatibility claim.

The application still accepts **synthetic data only**. This offline framework reads already authorized, consented/de-identified captures from an explicitly supplied local root. It does not acquire, copy, save, redact, upload or log patient inputs. No authentic capture is added by this phase. Do not put identifiable captures in the repository, CI artifacts, graph output, screenshots, terminal output, or the web UI.

## Workflow

1. Agree on authorization, de-identification, access and retention outside this prototype before gathering captures. A reviewer/consent reference in a manifest records an existing process; it is not evidence of legal authorization by itself.
2. Save the approved de-identified **verbatim logical clipboard text** as UTF-8, preserving tabs, whitespace, Unicode and line endings. Do not run cleanup/normalization. Record the copying application/build/version, copy surface, OS/browser and locale in the source evidence. These bytes are the capture artifact, not a claim to reconstruct clipboard-internal UTF-16 bytes.
3. Keep independent source-UI evidence locally (reviewed screenshot/manual evidence packet). Record the exact metadata and per-field definitions described below. No inference from a plausible filename, a source dropdown, or published documentation substitutes for the real capture.
4. Independently author the lexical gold output and field-level canonical expectations, checking the actual source UI. **Do not generate authentic gold by copying the parser's current output**; that only tests the implementation against itself. Every known canonical component needs an evidence locator in the source evidence; omitted or null components stay UNKNOWN. The neutral synthetic test helper exercises mechanics only and is not an authentic-gold authoring tool.
5. Hash the raw, expected and source-evidence artifacts with SHA-256. Populate a local manifest entry, initially PENDING. The schema is `schemas/vendor-fixture-manifest.v1.json`. Expected artifacts follow `schemas/vendor-fixture-expected.v1.json`.
6. Require two distinct approving reviewers, independent of the capture operator, including an orthodontist. Each review binds **all three exact hashes** and includes a real recorded timestamp with timezone. Capture metadata is not generated by the software. Reviewer identities, qualifications, consent and authenticity must be checked by the responsible organization; the program cannot authenticate human assertions.
7. Mark the entry REVIEWED only after that process. Check it with the read-only verifier. Any byte/context/expected-output change invalidates the old hashes/reviews and any previously approved release digest. A rejection, missing qualification, duplicated reviewer, stale hash or missing evidence cannot satisfy the review gate.
8. Passing fixture/oracle checks **does not enable normalization**. A separate code-reviewed release must register the exact approved bundle digest and define supported scope. The shipped release allowlist is empty. Do not add release digests or vendor mappings until real evidence has been reviewed. Revocation is separate and overrides approval.

Windows PowerShell, from the backend folder:

```powershell
.\.venv\Scripts\python.exe scripts\verify_vendor_fixtures.py
```

The shipped empty manifest returns **exit code 2**, `NO_AUTHENTIC_ORACLES`; this is intentional, not a passing vendor gate.

For future authorized artifacts already held in a controlled local location:

```powershell
.\.venv\Scripts\python.exe scripts\verify_vendor_fixtures.py --manifest 'D:\approved-captures\manifest.json' --fixture-root 'D:\approved-captures'
```

Exit 0: reviewed artifact integrity and exact lexical oracle checks passed, with **no compatibility approval**. Exit 1: invalid/incomplete evidence, unavailable/unsafe path, hash or oracle mismatch. Diagnostics contain static codes/counts only, never raw content, expected tokens, reviewer details or paths.

## Manifest and expected outputs

Each entry records the pseudonymous fixture ID, AUTHENTIC kind, actual application and exact version, PENDING/REVIEWED/REVOKED status, operator/capture timestamp, existing consent/de-identification references, artifact paths/hashes, submitted lexical metadata, and independent review records. The `submission_context` has empty `raw_text`; the verifier reads the raw artifact separately, preserving bytes. This uses internal `LexicalInput`, not the HTTP-only synthetic-data confirmation contract, so authentic evidence is never mislabeled synthetic.

Paths must be relative to the authorized root. Absolute/drive/UNC/URL/parent-traversal paths and resolved symlinks outside that root are refused. Limits are 1 MiB for manifest/raw, 16 MiB for source evidence and 32 MiB for expected JSON. Files are opened read-only; there is no fetching, writing, automatic discovery or application-startup loading.

Expected output contains the independently reviewed complete lexical result and optional assertions for individual measurement components. Original raw IDs/tokens/spans/Decimal strings remain in the lexical result. Canonical component names are:

```text
source_application, source_version, tooth_identifier, notation, dentition,
arch, axis, unit, sign, direction, plan_mode, reference_basis, scope,
stage_index, stage_kind, coordinate_frame, comparison_left_plan,
comparison_right_plan, comparison_operation
```

Values are explicit reviewed strings with evidence locators, or null for UNKNOWN. Never use zero as an unknown placeholder. A missing component is not supplied from a user claim or another field. Canonical tooth identifiers must state the approved target notation/namespace in the reviewed codebook; a raw `13` by itself is not a normalized anatomical identity. No generic FDI/Universal/Palmer or vendor axis/direction conversion table ships here.

The checked bundle is bound to raw/expected/source evidence hashes, complete input metadata, parser/schema/adapter version, cell/header/tooth provenance and lexical statuses. There is **no nearest-version matching, no cross-fixture extrapolation, and no general vendor normalization algorithm**. The current projection can only reproduce explicitly reviewed components of an identical approved fixture/context. New input or a changed context needs new matching evidence or a separately developed and validated versioned adapter in a future authorized task.

## Precise authentic sample request

Collect the following **for each exact source build/version, copy surface, locale and format that will be claimed as supported**. Do not create synthetic substitutes when a vendor does not offer a variant; record it as unsupported/not available.

| ClinCheck | Matched crown-center and virtual-root-apex views covering linear and angular fields; verify each field's reference meaning rather than treating root-view angles as root torque |
| ClinCheck | Each available FDI, Universal and Palmer export variant that will be supported, with independent notation/dentition/arch identification |

| Both | Both arches; mirrored left/right teeth; every exported axis; positive/negative/unsigned/zero values and each literal direction-code variant; relevant tooth groups and third molars where supported |
| Both | Permanent, primary or mixed dentition **only where actually supported and intended**; pontic/excluded/fixed/missing tooth indicators require independent verified status and must not be inferred from an absent column |
| Both | Blank cells, dash/N/A markers, explicit zero and unlisted axes, with source-UI confirmation of what each represents |
| Both | Every actually serialized orientation/delimiter/header variant, reordered columns/rows, locale decimal/unit formatting, Unicode symbols, precision and clipboard newline variants |
| Both | Unsupported revisions/layout drift, conflicting metadata and malformed examples, clearly distinguished from authentic supported captures and from synthetic fault-injection tests |

Every capture needs:

- Actual application/build/version, copy surface, OS/browser, locale/decimal convention, encoding and exact capture hash.
- Pseudonymous case/plan IDs and capture timestamp/operator; comparison operand IDs and source-defined operation when applicable.
- Explicit notation, dentition, arch, tooth presence/status metadata when available, and the exact intended canonical tooth identity.
- Original row/column headers and cell tokens, exact numerical precision, units, per-axis literal sign/direction conventions **for the tooth/arch concerned**, coordinate frame and any mirrored-side behavior.
- Plan mode, per-field crown/root/cusp reference basis, total/cumulative/incremental/stage-specific scope, stage index/identifier/kind, baseline and endpoint definitions. Last cumulative and total are not assumed equivalent.
- Evidence locations linking **each** canonical expectation to the capture/source UI; two independent reviews of those exact artifacts and hashes, with unresolved items explicitly UNKNOWN.

## Honest status and limitations

Synthetic plumbing tests use application `TEST_ONLY`, opaque test axes/identities/directions, and status TEST_ONLY. They have no fabricated independent reviews and cannot become VERIFIED, even if their digest is placed in an approval set. Production vendor mappings remain disabled.

Hash equality verifies artifact integrity; it does not prove authenticity, reviewer independence, clinical truth or regulatory approval. Expected-output agreement proves matching behavior on that fixture, not compatibility with other versions or patient populations. No clinical rules, treatment recommendations, staging calculations, angular composition, basis transforms or unit conversion are performed.
